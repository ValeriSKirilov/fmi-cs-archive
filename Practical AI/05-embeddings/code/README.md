# Упражнение 5: код

Практическа част към Лекция 5. Превръщаме текст във вектори (embeddings),
смятаме косинусовото сходство **на ръка**, правим малко семантично търсене и го
сравняваме с пълнотекстовото (BM25).

Задачите са три и кодът, който пишете, е малко: около шест реда. Повечето време
отива за пускане на скриптовете и за отговори на въпросите в тях. Там е и
същината на упражнението.

## Всичко върви локално, без ключ и без сметка

Упражнението ползва **локални** embedding модели през Ollama. Математиката е
една и съща, независимо кой модел създава векторите, а тя е темата. Така всеки
може да пуска всичко безплатно, офлайн и колкото пъти иска.

Облачен вариант (OpenAI) има през `EMBED_PROVIDER=openai` в `embeddings_util.py`,
**само за сравнение**. Нито една задача не се нуждае от него.

> **Защо `bge-m3`, а не популярните `nomic-embed-text` или `all-minilm`:** те са
> обучени основно на английски и на български връщат почти случайни резултати.
> `bge-m3` е многоезичен. Задача 3 показва разликата на живо, а изводът е
> практичен: embedding моделът се избира според **езика** на данните, не според
> класация на английски benchmark.

## Принцип на курса: първо „под капака“, после готовото

> Косинусовото сходство пишете сами в `embeddings_util.py`, точно по формулата
> от лекцията.
>
> Затова `cos_sim` е на **обикновен Python, без numpy**: векторът е списък от
> числа, `dot` е сума от произведения, `norm` е корен от сумата на квадратите.
> BM25 е даден наготово. Лекцията обяснява идеята му (честота на думата, IDF и
> нормализация по дължина), а тук ни интересува кога печели и кога губи.

## Задачи

1. **От текст до сходство.** Попълнете `dot`, `norm` и `cos_sim` в
   `embeddings_util.py` (по един ред), после пуснете `01_vectors.py`. Той
   показва, че размерността е свойство на модела, че векторите са нормализирани
   (затова `cos_sim` е равно на `dot`), че един и същ текст дава един и същ
   вектор и **капана с отрицанието**: сходство не значи съгласие.
2. **Семантично търсене срещу BM25.** Попълнете `search()` в `02_search.py`
   (около три реда) и сравнете двата подхода: кой печели при синоним
   („превозно средство“) и кой при точен код (`SKU-4471`).
3. **Изборът на модел.** Без нов код: пуснете `02_search.py --model all-minilm`
   и сравнете попаденията с тези на `bge-m3`. Различна размерност означава
   различни пространства, а смяната на модела означава преиндексиране.

**Бонус:** междуезично търсене, `02_search.py --query "vehicle"` с `bge-m3`.

**Демо (не е задача):** `demo_scan_timing.py` показва, че линейното търсене
става по-бавно пропорционално на броя вектори. Това е мостът към Тема 6
(векторни бази).

## Подготовка

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

ollama pull bge-m3        # многоезичен, по подразбиране (~1.2 GB)
ollama pull all-minilm    # английски, само за задача 3 (~45 MB)
```

Няма `.env` за попълване: упражнението не изисква ключ.

## Стартиране

```bash
python solutions/01_vectors.py
python solutions/02_search.py
python solutions/02_search.py --model all-minilm
python solutions/02_search.py --query "vehicle"
python demo_scan_timing.py
```

В `starter/` са същите файлове с `TODO`, а в `solutions/` са готовите решения.

## Бележки

- **Едно пространство:** не смесвайте вектори от различни модели (`bge-m3` с
  1024 измерения и `all-minilm` с 384). Дори праговете („над 0.6 значи
  релевантно“) не се пренасят от модел на модел.
- **Нормализирани вектори:** `bge-m3` връща вектори с дължина 1, затова
  `cos_sim` е равно на `dot`. Пълната формула работи и за ненормализирани.
- **Сходство не значи съгласие:** „пристигна навреме“ и „не пристигна навреме“
  излизат много близки. Търсенето връща текстове „по темата“, а дали текстът
  потвърждава твърдението, е отделна стъпка (Тема 8).
