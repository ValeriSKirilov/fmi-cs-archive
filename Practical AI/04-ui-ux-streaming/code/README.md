# Упражнение 4 — код

Практическа част към Лекция 4: правим чакането на модела **поносимо** чрез
стрийминг. Две части: **A** — суров SSE на Python (под капака, практическа задача);
**B** — **разглеждане на 3 различни frontend решения** с примери и обяснения (не
задача с TODO), за да сравним компромисите.

## Принцип на курса: първо „под капака“, после библиотека

> В Част A изграждаме стрийминга **на ръка** — FastAPI, който форматира SSE събития, и
> клиент с `fetch` + `ReadableStream` reader. Чак след като видим суровия
> механизъм, в Част B ползваме `streamText` / `useChat` съзнателно, знаейки какво
> капсулират. (Вижте правилото от Теми 2–3.)

### Какво се вижда в задачите

- **Задача 3** — „Тест: нарязан поток“: наивният клиент дава `Unexpected token 'd'`
  (капан 1: парче ≠ събитие); с `buffer` кирилицата става `Зд��ав��й` (капан 2:
  буква, разцепена между парчета); с `{ stream: true }` текстът излиза правилно.
  *Забележка:* `json.dumps(delta)` по подразбиране escape-ва кирилицата до `\uXXXX`
  и капан 2 нямаше да се прояви; затова сървърът ползва `ensure_ascii=False`, както
  прави реалният API (суров UTF-8).
- **Задача 4** — `/chat` (async) логва `потокът е затворен` веднага след „Спри“;
  `/chat_sync` не, а Ollama продължава да генерира (TTFT на следващата заявка: ~25 s срещу ~3 s).

## Част B — три frontend решения за сравнение (`frontend/`)

Тук **не решаваме задача** — разглеждаме **три работещи подхода** за същия стрийминг
чат и сравняваме кога кое е уместно. Пълното сравнение (таблица, trade-offs, команди
за пускане) е в [`frontend/README.md`](frontend/README.md).

- **`approach-1-nextjs/`** — Next.js + Vercel AI SDK (`useChat`/`streamText`). Един
  проект, без CORS; стандартният начин за ползване на SDK-то и Generative UI.
- **`approach-2-vite-fastapi/`** — чист React (Vite) върху нашия FastAPI backend от
  Част A, със **собствен hook** `useChatStream` (без SDK). Показва „какво прави
  `useChat` под капака“; ключът остава в Python сървъра.
- **`approach-3-vite-node/`** — чист React (Vite) + малък Node сървър (Hono) с AI
  SDK. Запазва удобството на SDK-то, но с втори процес и CORS.

Основната поука: **API ключът не може да е в браузъра**, затова backend е нужен и при
трите — разликата е *къде* седи и *колко* от работата поема библиотеката.

## Бележки

- **Реална vs. възприемана латентност**: стриймингът не прави модела по-бърз;
  прави UX-а поносим. Мерете **TTFT**, не само общото време.
- **SSE рамкиране**: събитията се разделят с празен ред (`\n\n`). Токен може да
  съдържа нов ред, затова в `01_sse_server.py` JSON-кодираме делтата
  (`json.dumps`), а клиентът я `JSON.parse`-ва — иначе рамкирането се чупи.
- **Без буфериране**: `X-Accel-Buffering: no` спира буферирането от прокси (nginx),
  иначе отговорът идва накуп.
- **Отмяна**: `AbortController` спира и мрежовата заявка, и (при коректен сървър)
  генерацията — иначе токените се харчат напразно.
- **Версии на SDK-то**: Vercel AI SDK се развива бързо (тук е закована v5: `parts`,
  `tool-<name>` части; актуалната е v7). Сверявайте се с текущата документация.
- Моделите по подразбиране: локален `bggpt:4b` (без ключ); по избор `gpt-6-luna`,
  `claude-haiku-4-5` (Python); в TS route-ите по подразбиране е локален Ollama с `llama3.2` (`ollama pull llama3.2`).
